# إحصائيات SDK: الاستلام والعرض والنقر

هذه الإضافة لا تجعل قبول FCM دليلًا على التسليم. الرسائل القديمة لا تملك إيصالات ولا يمكن استعادة إحصائياتها بأثر رجعي.

## الأحداث

- `received`: وصل callback إلى SDK.
- `displayed`: نجح `NotificationManager.notify` بعد فحص إذن الإشعارات والقناة. هذا تأكيد نشر الإشعار برمجيًا، وليس مشاهدة المستخدم له أو قراءته.
- `clicked`: وصل Intent النقر إلى SDK. النقر يؤكد كذلك عرض الإشعار، ويُسجل حتى إن كانت الوجهة غير مدعومة. لا يعني نجاح فتح الرابط.
- `display_failed`: تعذر العرض بسبب الإذن أو تعطيل الإشعارات/القناة أو فشل عملية النشر. لا يُعامل ذلك كإلغاء اشتراك.

تربط قاعدة البيانات كل إيصال برسالة وجهاز مسجلين. رمز عشوائي 256 بت لكل مستلم يُرسل ضمن بيانات FCM، ويُحفظ تجزئته فقط بالخادم. لا يمكنه إرسال إشعارات أو قراءة بيانات؛ يتيح أحداث إيصال واحد لمدة 30 يومًا. لا يوجد مفتاح Admin داخل SDK. لا يظهر الرمز في سجل الرسائل أو التقرير. هذا بروتوكول قياس ثقة من العميل، وليس إثباتًا مشفرًا أن إنسانًا شاهد الإعلان؛ العميل المعدل أو حامل الرمز قادر على تزوير أحداث إيصال نفسه.

## حساب الأرقام

`Delivered` = عدد الأجهزة المستلمة الفريدة التي أكدت الاستلام (`receivedAt`). العرض أو النقر يؤكدان الاستلام أيضًا.
`Displayed` = عدد الأجهزة التي أكدت نشر الإشعار، وهو منفصل عن وصول الرسالة.
`Sent` = عدد محاولات الإرسال إلى الأجهزة المسجلة المستهدفة (`result.total`)، وليس عدد تثبيتات SDK غير المسجلة. `Accepted by FCM` يعرض عدد المحاولات المقبولة منفصلًا. طلب topic واحد لا يمثل عدد مستخدميه، لذلك Sent للمستخدمين فيه N/A.
`Clicks` = المستلمون الفريدون الذين نقروا، لا عدد مرات الضغط المتكرر.
`CTR` = Clicks / Delivered × 100. يعرض N/A عند انعدام المقام أو عدم وجود تتبع.
`Failed` = محاولات إرسال رفضها FCM. يعرض التقرير `Display blocked / failed` بشكل منفصل. عدم وصول إيصال لا يُعد فشلًا.
`Unsubscribed` = الرموز التي أعاد FCM أنها غير صالحة/غير مسجلة أثناء إرسال هذه الرسالة. ليس تعدادًا مؤكدًا لعمليات إلغاء الاشتراك البشرية أو إلغاء تثبيت التطبيق في الزمن الحقيقي.
الأحداث متسامحة مع التكرار والوصول خارج الترتيب؛ سجل النقر لا يعيد احتساب المستلم. قد تتحسن الأرقام لاحقًا عند عودة الشبكة. جميع الأرقام المستندة إلى الإيصالات تمثل التغطية المرصودة فقط.

## أوضاع الإرسال

1. الوضع المعتاد Notification + Data يحافظ على الصور. في الخلفية يعرض FCM الإشعار مباشرة ولا يستدعي خدمة SDK؛ لذلك قد لا يُرصد الاستلام أو العرض إلا لاحقًا عند النقر. يعرض التقرير تحذير التغطية الجزئية، وتظهر * بجوار CTR في الجدول. لا يجوز اعتبار هذه النسبة CTR شاملًا للحملة.
2. يختار الخادم تلقائيًا Data Messages للنصوص المرسلة إلى أجهزة مسجلة، دون خيار Delivery tracking في النموذج. SDK المحدث يعرض الإشعار ويسجل الاستلام والعرض في المقدمة والخلفية. يدعم النص والروابط حاليًا؛ يختار الخادم الوضع المعتاد تلقائيًا للصور وTopics كي لا يفقد الصور أو يدعي وجود إيصالات فردية للـTopics. SDK القديم غير متوافق مع وضع Data الجديد؛ حدّث التطبيقات قبل الإرسال. رسائل بدون وجهة تستخدم إجراء app/main لفتح التطبيق فقط.
3. Topics وFirebase Console لا تحصل على رموز مستلمين فردية من هذه اللوحة: إحصائياتها N/A. لا يُعد قبول طلب Topic جهازًا واحدًا.

حتى وضع Data لا يضمن الوصول أثناء force-stop، ولا يتجاوز قيود البطارية أو Android أو الشبكة. لا تتحول أجهزته الصامتة إلى Failed تلقائيًا.

## إعداد التطبيق

في Builder:

```java
.telemetryEndpoint("https://your-trusted-server.example/api/events")
```

الإعداد اختياري ومعطل افتراضيًا. وجهة رفع الإحصائيات ثابتة يحددها التطبيق المضيف؛ لا تؤخذ من الرسالة. HTTPS إلزامي باستثناء loopback في APK قابل للتصحيح. يجب أن تكون واجهة `/api/events` قابلة للوصول من الهاتف. الخادم المحلي الحالي يستمع على loopback ويتحقق من Host؛ نشره للعموم يحتاج إعداد TLS ووكيل موثوق منفصل، ولا يُعرض منفذ لوحة الإدارة مباشرة للإنترنت.

لاختبار USB:

```powershell
adb reverse tcp:4310 tcp:4310
gradle :sample:assembleDebug -PopenpushTelemetryEndpoint=http://127.0.0.1:4310/api/events
```

نسخة debug التجريبية تسمح HTTP محليًا؛ نسخة release لا تسمح به. تجنب إدخال بيانات شخصية في URL endpoint. JobScheduler يرفع طابورًا محليًا خاصًا بالتطبيق مع إعادة محاولة وخلفية شبكة، بحد 1000 حدث و30 يومًا، وبحد 20 حدثًا لكل تشغيل. Android يحدد موعد التشغيل، وقد يتأخر الرفع. أضيف JobService محمي بـ BIND_JOB_SERVICE وإذن RECEIVE_BOOT_COMPLETED لاستمرار الجدولة بعد إعادة التشغيل. لا تُسجل خدمة FirebaseMessagingService إضافية. اترك تفويض الخدمة الحالية وonCreate/onNewIntent كما هو. على المضيف استثناء `openpush.receipts.v1.xml` من النسخ الاحتياطية، أو تعطيل النسخ الاحتياطي كما في sample؛ طابور الإيصالات يحتوي رموز صلاحية محدودة.

لا توجد هجرة تدعي تسليم الرسائل السابقة. تتطلب إضافة API إعادة تشغيل الخادم الجاري بنفس قاعدة بياناته.

## التحقق

سيُسجل التنفيذ الفعلي ونتائج الهاتف في نهاية العمل. اختبارات Sender البديل والأحداث المصطنعة لا تثبت وصول FCM الحقيقي.

- هاتف Android متصل عبر USB: ثُبتت نسخة QA محدثة وشُغل TelemetryDeviceTest بنجاح (اختبار واحد). نُشرت رسالتان محليتان عبر SDK، ووصل إلى API المعزول 2 received و2 displayed و2 clicked فريدة؛ أُرسل PendingIntent الأول مرتين وبقي احتسابه مرة واحدة. نتائج الخادم لا تؤكد توقيت النقر أو أن النقرتين كانتا يدويتين؛ مصدر الرسائل محلي في الاختبار.
- لم تُختبر في هذا التنفيذ رسالة FCM حقيقية بعد تفعيل التتبع، أو الانقطاع الطويل للشبكة/إعادة تشغيل الهاتف، أو force-stop، أو SDK قديم. لم يُعتبر أي منها ناجحًا.
- أدوات shell ترى قاعدة مختلفة عن اللوحة المفتوحة. لم تُبدل قاعدة المستخدم أو بيانات اعتماده. اختبار Dashboard → FCM → الهاتف → إحصائيات اللوحة ينتظر إعادة تشغيل خادم اللوحة الأصلية وتحميل endpoint الجديد.

الأثر المنقح دون رموز الإيصالات: `verification/telemetry-device-results.json`.

### النسخة النهائية على الهاتف

ثُبّت APK النهائي بنجاح بعد الاختبار، مع `openpushTelemetryEndpoint=http://127.0.0.1:4310/api/events`، وربط adb reverse للمنفذ 4310. أُلغي ربط 4311 وأوقف مستقبل QA. أُعيد اختبار ReceiptQueueTest (3 اختبارات) بعد تحسين التعامل مع فشل الجدولة، ونجح assembleDebug النهائي. ينتظر اختبار FCM الحقيقي إعادة تشغيل خادم اللوحة الأصلي؛ إعادة تثبيت APK وحدها لا تثبت اكتمال الدورة.


تحديث: أزيل اختيار Delivery tracking من واجهة الإنشاء. الخادم يتجاهل اختيار trackingMode القديم عند تحديد النقل الجديد. حماية requestKey تحتفظ بنتيجة الإرسال السابق حتى لو تغير هذا الحقل التقني، ولا تعيد الإرسال. تشغيل مسار الإيصالات تلقائي لا يلغي قيود FCM أو الحاجة إلى endpoint مضبوط في SDK.

### تحديث 2026-10-19

جدول الرسائل: Name، Labels، Status، Started sending، Created at، Delivered، CTR، Actions. التصنيفات غير المسجلة تعرض —. وقت بدء الإرسال يسجل عند بدء المحاولات الفعلية، والرسائل السابقة التي لم تسجله تعرض — دون تخمينه من وقت الإنشاء. بقي Failed عدد إخفاقات طلبات FCM، وUnsubscribed عدد الرموز التي ثبت عدم صلاحيتها أثناء إرسال هذه الرسالة؛ ليس إجمالي عمليات حذف التطبيق. الأحداث المفقودة لا تُعد فشلًا.

الواجهة تحسب CTR من received حتى عند استلام استجابة API قديمة كانت تستخدم displayed كمقام. نجحت 33 اختبارات خادم و6 اختبارات ويب، ومنها الفصل بين الاستلام والعرض وبين محاولات الإرسال وقبول FCM. لا تُنشئ هذه التعديلات إيصالات للرسائل السابقة.

### تعريفات التفاعل المحدثة — 2026-10-19

- Sent: محاولات الإرسال إلى الأجهزة المسجلة المستهدفة. لا يمكن معرفة تثبيت SDK لم يسجل جهازه أصلًا.
- Delivered: استلام مؤكد مع استبعاد تعطيل الإشعارات والفشل المثبت؛ تأكيد العرض/النقر اللاحق يغلب الفشل السابق. لا نحسبه Sent ناقص الباقي لأن هناك رسائل متأخرة/غير مؤكدة.
- Total clicks: عدد الأجهزة التي وصل منها حدث clicked، مرة واحدة لكل رسالة وجهاز.
- Unsubscribed: حدث notification_disabled من SDK لهذا المستلم عند منع إذن الإشعارات أو القناة. لا يوجد رصد فوري لتغيير الإذن والتطبيق متوقف؛ يظهر عند وصول حدث جديد. الرموز غير المسجلة في FCM منفصلة في Invalid device tokens.
- Failed: إخفاق طلب الإرسال أو فشل العرض المثبت، دون احتساب التعطيل أو الرسائل المتأخرة أو عدم النقر كفشل.
- Unconfirmed / delayed: الحالات الباقية دون حكم تلقائي بالفشل.
- CTR = النقرات الفريدة ÷ Delivered × 100؛ صفر بعد استلام مؤكد دون نقر، وN/A إذا لم يوجد مقام مؤكد.

تضيف الهجرة permissionDisabledAt وsendFailedAt دون إعادة تفسير unsubscribed القديم (الذي كان يعني رمز FCM غير صالح). الأحداث القديمة display_failed لا تثبت نوع سبب الفشل ولا نستنتج منها تعطيل الإذن بأثر رجعي. الإشعارات القديمة بلا op_receipt لا يمكن ربط نقراتها بالتقرير، فلا تُولّد أرقام تاريخية. يلزم تشغيل الخادم المحدث بنفس قاعدة بياناته قبل تثبيت أحداث notification_disabled؛ الخادم القديم لا يقبل هذا الحدث.
